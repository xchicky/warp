# M8.3: Read-Only Autoexecute Allowlist Expansion V2

## Summary

Expand the local OpenAI-compatible agent's static read-only shell autoexecute allowlist beyond the M8.2 Git-only set. This milestone adds a small, explicit, fail-closed set of common inspection commands for structured data, environment inspection, terminal multiplexers, container listing, and Kubernetes inspection.

The existing `run_shell_command` card, terminal execution path, output capture, cancellation, provider resume behavior, user denylist precedence, and visible command history remain unchanged. The user skips only the approval click for commands that the local classifier can prove are read-only.

## Problem

After M8.2, local-agent repository workflows still pause on common inspection commands that agents naturally use while diagnosing projects:

- Querying JSON/YAML output from existing files or command output.
- Inspecting environment variables.
- Listing tmux sessions, windows, and panes.
- Listing Docker containers/images.
- Inspecting Kubernetes resources.

The expansion must not become a generic shell-autonomy mode. Ambiguous command shapes must keep requiring approval.

## Goals

1. Add a narrow set of read-only commands to the M6.1/M8.2 static classifier.
2. Keep explicit allowlists per command; do not rely on broad "read-only" claims from the model.
3. Preserve the global fail-closed parser for shell syntax, wrappers, mutating commands, network/file-transfer commands, package managers, and editors.
4. Preserve existing command cards, audit history, bounded output capture, cancellation, user denylist precedence, and local-provider resume behavior.
5. Require installed-app e2e before declaring completion.

## Non-Goals

1. Do not add `xargs`, `awk`, or `sed`, including `sed -n`; those require a separate spec gate because they can proxy or hide mutating behavior.
2. Do not add file-write tools, MCP tools, web tools, subagents, or plan-mode shell execution.
3. Do not add broad shell wrappers or command-composition support.
4. Do not add package-manager or language runtime commands such as `npm`, `cargo`, `python`, `pip`, `ruby`, or `node`.
5. Do not autoexecute Docker or Kubernetes commands that can mutate state or attach to running workloads.
6. Do not trust model-provided `is_read_only`, `is_risky`, or similar fields.

## Behavior

1. `is_local_autoexecute_safe_command(command)` remains the sole source of static local autoexecute eligibility for shell commands.
2. If `LocalAgentShellExecution` and `LocalAgentAutoExecuteSafeCommands` are enabled, commands matching the allowlisted shapes below autoexecute through the existing shell command action path.
3. If a command does not positively match the allowlist, existing visible approval behavior remains unchanged.
4. Existing user denylist settings take precedence over static safe-command autoexecute.
5. Existing forbidden shell syntax remains globally denied before command-specific classification: command chaining, pipes, redirection, command substitution, process substitution, backgrounding, newlines, and shell wrappers.
6. Plan mode remains read-only and does not execute shell commands. A plan-mode model may propose these commands, but direct `run_shell_command` calls remain unavailable in plan mode.
7. Approved-plan implementation remains normal mode: newly allowlisted commands may autoexecute when the same feature flags and user settings permit autoexecution.
8. Autoexecuted commands still render normal command cards and captured output. There is no silent background execution.

## New Static Allowlist

### `jq`

Allow JSON query commands that run an inline filter and do not load external jq programs or arbitrary input files.

Allowed examples:

- `jq . package.json`
- `jq '.scripts' package.json`
- `jq -r '.name' package.json`
- `jq --raw-output '.name' package.json`
- `jq -c '.[]' data.json`
- `jq --compact-output '.[]' data.json`
- `jq -s '.' a.json b.json`
- `jq --slurp '.' a.json b.json`
- `jq -n '{ok: true}'`
- `jq --null-input '{ok: true}'`
- `jq --arg name Warp '.name = $name' package.json`
- `jq --argjson count 3 '.count = $count' package.json`

Denied examples:

- `jq -i '.x=1' file.json`
- `jq --in-place '.x=1' file.json`
- `jq -f filter.jq file.json`
- `jq --from-file filter.jq file.json`
- `jq --rcfile custom.jq '.x' file.json`
- `jq --slurpfile extra ../../secret.json '.x' file.json`
- `jq --rawfile extra ../../secret.txt '.x' file.json`
- `jq --run-tests tests.jq`
- `jq '.x' file.json > out.json`

Implementation constraints:

- Use an explicit whitelist of accepted flags.
- Deny all flags that load filters/modules/files outside normal input operands.
- If a flag accepts a value, require the value shape explicitly; missing values require approval.
- Unknown flags require approval.

### `yq`

Allow Mike Farah `yq` read/query forms. This spec targets the Go `mikefarah/yq` CLI, not the Python wrapper that transcodes YAML through jq. The classifier cannot prove which binary is installed, so it must only allow forms that are read-only in the Mike Farah syntax and fail closed for script/file-loading or write forms.

Allowed examples:

- `yq . config.yml`
- `yq '.services' docker-compose.yml`
- `yq eval '.metadata.name' manifest.yml`
- `yq e '.metadata.name' manifest.yml`
- `yq -o=json '.' manifest.yml`
- `yq --output-format=json '.' manifest.yml`
- `yq -r '.metadata.name' manifest.yml`
- `yq --unwrapScalar '.metadata.name' manifest.yml`
- `yq -N '.metadata.name' manifest.yml`
- `yq --no-doc '.metadata.name' manifest.yml`

Denied examples:

- `yq -i '.x = 1' config.yml`
- `yq --inplace '.x = 1' config.yml`
- `yq eval -i '.x = 1' config.yml`
- `yq --from-file expression.yq config.yml`
- `yq -f expression.yq config.yml`
- `yq --split-exp '.metadata.name' config.yml`
- `yq '.x' config.yml > out.yml`
- `python -m yq '.x' config.yml`

Implementation constraints:

- Allow only `yq`, `yq eval`, and `yq e` query shapes.
- Use an explicit whitelist of accepted output/read flags.
- Deny in-place, expression-from-file, split-output, and unknown subcommands.
- Unknown flags require approval.

### `env`

Allow environment inspection forms only.

Allowed examples:

- `env`
- `env --null`
- `env PATH`
- `env PATH HOME SHELL`

Denied examples:

- `env -i`
- `env --ignore-environment`
- `env VAR=value`
- `env VAR=value printenv`
- `env PATH=/tmp git status`
- `env sh -c pwd`
- `env -u PATH`
- `env --unset=PATH`

Implementation constraints:

- Allow no arguments, `--null`, and variable-name operands.
- A variable-name operand must be a plain environment variable identifier (`[A-Za-z_][A-Za-z0-9_]*`).
- Deny assignments, command operands, unset/ignore-environment flags, and unknown flags.

### `printenv`

Allow environment variable printing forms.

Allowed examples:

- `printenv`
- `printenv PATH`
- `printenv PATH HOME`
- `printenv --null`
- `printenv -0`

Denied examples:

- `printenv PATH > out`
- `printenv $(rm x)`
- `printenv --help | tee out`
- `printenv --unknown`

Implementation constraints:

- Allow no arguments, `--null`, `-0`, and variable-name operands.
- Unknown flags require approval.
- Existing forbidden shell syntax still rejects redirection and command substitution.

### `tmux`

Allow a narrow set of tmux inspection commands.

Allowed examples:

- `tmux list-sessions`
- `tmux ls`
- `tmux list-windows`
- `tmux list-panes`
- `tmux list-panes -a`
- `tmux list-panes -F '#{pane_id} #{pane_current_command}'`
- `tmux display-message -p '#S:#I.#P'`

Denied examples:

- `tmux attach`
- `tmux attach-session`
- `tmux new-session`
- `tmux kill-session`
- `tmux kill-pane`
- `tmux send-keys ls Enter`
- `tmux capture-pane -p > pane.txt`
- `tmux source-file ~/.tmux.conf`

Implementation constraints:

- Allow only `list-sessions`, `ls`, `list-windows`, `list-panes`, and `display-message -p`.
- Allow read-only target and format flags needed for those commands, such as `-t`, `-a`, `-F`, and `-f` only where tmux documents them as filters/formats for listing.
- Deny all other tmux subcommands.
- Unknown flags require approval.

### `docker`

Allow Docker local daemon listing commands only.

Allowed examples:

- `docker ps`
- `docker ps -a`
- `docker ps --all`
- `docker ps --filter status=running`
- `docker ps --format '{{.Names}}'`
- `docker images`
- `docker image ls`
- `docker images --filter dangling=false`

Denied examples:

- `docker run hello-world`
- `docker start app`
- `docker stop app`
- `docker rm app`
- `docker rmi image`
- `docker exec app sh`
- `docker kill app`
- `docker pull alpine`
- `docker push repo/image`
- `docker logs app`

Implementation constraints:

- Allow only `docker ps`, `docker images`, and `docker image ls`.
- Allow display/filter flags that do not change daemon state.
- Deny commands that start, stop, attach, exec, delete, build, pull, push, or stream logs.
- Unknown Docker subcommands require approval.

### `kubectl`

Allow Kubernetes inspection commands only.

Allowed examples:

- `kubectl get pods`
- `kubectl get pods -n default`
- `kubectl get deployments --all-namespaces`
- `kubectl get pods -o wide`
- `kubectl get pods -o yaml`
- `kubectl describe pod my-pod`
- `kubectl version --client`
- `kubectl cluster-info`
- `kubectl config view`
- `kubectl config current-context`
- `kubectl config get-contexts`

Denied examples:

- `kubectl apply -f deploy.yml`
- `kubectl create deployment app --image=nginx`
- `kubectl delete pod app`
- `kubectl patch deployment app -p '{}'`
- `kubectl replace -f deploy.yml`
- `kubectl scale deployment app --replicas=3`
- `kubectl exec pod -- sh`
- `kubectl port-forward pod/app 8080:80`
- `kubectl logs pod/app`
- `kubectl config set-context prod`
- `kubectl config use-context prod`

Implementation constraints:

- Allow only `get`, `describe`, `version`, `cluster-info`, and `config` read-only subcommands.
- For `kubectl config`, allow only `view`, `current-context`, and `get-contexts`.
- Deny all mutating Kubernetes commands and all proxy/attach/streaming commands.
- Unknown flags require approval unless explicitly whitelisted for an allowed read-only form.

## Cross-Command Deny Rules

The implementation must keep existing global rejects and add equivalent command-specific hostile-config rejects where applicable:

1. Shell wrappers remain denied: `sh`, `bash`, `zsh`, `fish`, `pwsh`, `eval`, `exec`, `source`, and `.`.
2. Mutating filesystem commands remain denied: `rm`, `mv`, `cp`, `touch`, `mkdir`, `rmdir`, `chmod`, `chown`, `sudo`, and `tee`.
3. Network/file-transfer/package/editor commands remain denied unless explicitly allowed above: `ssh`, `scp`, `rsync`, `curl`, `wget`, `nc`, `netcat`, `telnet`, `cargo`, `npm`, `pnpm`, `yarn`, `python`, `python3`, `pip`, `pip3`, `vim`, `vi`, `nano`, `emacs`, and `sed`.
4. Shell syntax remains denied: `;`, newline, `&&`, `||`, `|`, `&`, `>`, `>>`, `<`, `<<`, `<<<`, `2>`, `&>`, `$(`, backticks, `<(`, and `>(`.
5. Commands with hostile config/script-loading flags require approval, including jq/yq filter-from-file or rcfile forms and kubectl config write forms.

## Acceptance Criteria

1. `jq` inline query forms autoexecute when M6.1 flags/settings permit.
2. `jq` script/file-loading, in-place, test-running, and shell-redirection forms require approval.
3. Mike Farah `yq` query forms autoexecute when M6.1 flags/settings permit.
4. `yq` in-place, expression-from-file, split-output, Python-wrapper, and shell-redirection forms require approval.
5. `env` environment-listing and variable-name forms autoexecute.
6. `env` command execution, assignment, unset, and ignore-environment forms require approval.
7. `printenv` variable-printing forms autoexecute.
8. `printenv` unknown-flag and shell-injection forms require approval.
9. `tmux list-*` and `display-message -p` forms autoexecute.
10. Mutating or interactive tmux commands require approval.
11. `docker ps`, `docker images`, and `docker image ls` inspection forms autoexecute.
12. Mutating, attaching, deleting, pulling, pushing, building, or log-streaming Docker commands require approval.
13. `kubectl get`, `describe`, `version`, `cluster-info`, and read-only `config` forms autoexecute.
14. Mutating, attaching, proxying, port-forwarding, log-streaming, or context-mutating Kubernetes commands require approval.
15. Existing M8.2 Git allowlisted commands continue to autoexecute.
16. Existing M6.1 denied commands and forbidden shell syntax continue to require approval.
17. User denylist settings still override static local safe-command autoexecute for at least one newly allowlisted command.
18. Feature-flag-off behavior still requires approval for newly allowlisted commands.
19. The model cannot force autoexecute by setting or describing a command as read-only.
20. Plan mode still does not execute shell commands, including newly allowlisted commands.
21. Approved-plan implementation remains normal mode: new read-only commands may autoexecute, while file writes and non-allowlisted shell commands still follow existing approval behavior.

## Manual E2E Hard Gate

Run on an installed Dev build with `LocalAgentShellExecution` and `LocalAgentAutoExecuteSafeCommands` enabled.

1. In a repository with JSON/YAML files, ask the local agent to inspect JSON with `jq '.' package.json`.
2. Confirm `jq '.' package.json` runs without an approval click and still shows a normal command card/output.
3. Ask the agent to run `yq -i '.x = 1' config.yml`.
4. Confirm the `yq -i` command requires visible approval and does not autoexecute.
5. Ask the agent to run `docker ps`.
6. Confirm `docker ps` autoexecutes if Docker is installed and otherwise shows normal command output/error without an approval click.
7. Ask the agent to run `docker run hello-world`.
8. Confirm `docker run` requires visible approval.
9. Ask the agent to run `kubectl get pods`.
10. Confirm `kubectl get pods` autoexecutes if `kubectl` is installed and otherwise shows normal command output/error without an approval click.
11. Ask the agent to run `kubectl apply -f deploy.yml`.
12. Confirm `kubectl apply` requires visible approval.

Source-level tests are not enough for this milestone. At least `jq '.' package.json` autoexecute, `yq -i` denial, and `docker run` denial must be verified in the installed app before PM/user e2e completion.

## Implementation Notes

1. Extend `safe_shell_command.rs` with command-specific helper classifiers; do not add these commands to a broad top-level allowlist without arguments.
2. Keep explicit allow/deny lists near the helper that uses them.
3. Treat unknown flags as unsafe unless the spec explicitly allows them.
4. Prefer accepting common `--flag=value` and `--flag value` forms only when the value cannot be misread as another option or command.
5. Do not add path-containment logic in this PR. The safety boundary remains static command classification plus existing shell-command approval fallback.
6. Do not alter `BlocklistAIPermissions` policy semantics except to ensure newly classifier-safe commands flow through the existing local static safe-command path.
7. Do not change command output limits, terminal execution semantics, provider resume/finalize, telemetry shape, or command-card rendering.
8. Split the implementation if the diff expands beyond classifier helpers and focused tests.

## Risk Assessment

- **CLI dialect drift:** `yq` has multiple implementations. This spec targets Mike Farah `yq`; ambiguous Python-wrapper forms require approval.
- **Script/file loading:** jq/yq can load filters or auxiliary files. Deny file-loading flags until a separate path/read policy exists.
- **Daemon or cluster side effects:** Docker and Kubernetes CLIs have many mutating verbs. Use command-specific allowlists and deny unknown subcommands.
- **Shell injection:** Existing global forbidden syntax must remain first-gate behavior.
- **Network/cache side effects:** Docker/Kubernetes inspection commands may contact local daemons or clusters. The user accepted these V0 commands, but mutating or streaming operations remain out of scope.
- **Over-broad plan approval:** M8.1 plan approval must not become an auto-approve-all execution profile. This spec only changes normal-mode static read-only command classification.

## Escalation Conditions

Escalate before implementation continues if:

1. A proposed command or option cannot be confidently classified as read-only.
2. Supporting an allowlisted form requires shell redirection, pipes, command chaining, or shell wrapper support.
3. Supporting jq/yq safely requires parsing expression languages beyond simple flag classification.
4. Docker or Kubernetes read-only forms prove mutating or unsafe in practice.
5. The implementation needs approval-policy changes outside the existing local static safe-command path.
6. Tests reveal existing M6.1/M8.2 safe-command behavior regresses.
7. Installed-app e2e shows a mutating command autoexecutes or an allowlisted read-only command silently runs without a visible command card.

## PR Split

Single implementation PR is acceptable if the diff stays limited to:

- `app/src/ai/agent/local/safe_shell_command.rs`
- Existing local autoexecute / run-shell-command focused tests
- Permission or plan-mode tests needed for feature-flag, denylist, and plan-mode fallback coverage

Split if implementation discovers broader policy, UI, provider, or command execution changes are required.
