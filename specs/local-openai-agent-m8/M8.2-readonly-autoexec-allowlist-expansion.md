# M8.2: Read-Only Autoexecute Allowlist Expansion

## Summary

Expand the local OpenAI-compatible agent's static read-only shell autoexecute allowlist for a small set of Git inspection commands. The existing `run_shell_command` card, terminal execution path, output capture, and fail-closed approval behavior remain unchanged; the user only skips the approval click for commands that the local classifier can prove are read-only.

This is an incremental continuation of M6.1. It does not add a new autonomy mode and does not make plan approval auto-approve arbitrary implementation steps.

## Problem

M6.1 already removes approval friction for common inspection commands, but local-agent repository workflows still stall on several safe Git inspection commands that users and agents naturally use while planning or implementing:

- listing local branches
- inspecting remotes
- reading scoped Git configuration values
- describing the current commit
- inspecting line history with blame

The next expansion should preserve the M6.1 safety model: static local classification, explicit deny examples, fail closed on ambiguity, and visible command cards for everything that runs.

## Current State

`app/src/ai/agent/local/safe_shell_command.rs` owns the local static classifier:

- `is_local_autoexecute_safe_command(command)` rejects empty commands, forbidden shell syntax, unparseable shell words, disallowed top-level commands, and command-specific risky options.
- `GIT_ALLOWED_SUBCOMMANDS` currently allows `status`, `diff`, `log`, `show`, `rev-parse`, `ls-files`, and `grep`.
- `GIT_DENIED_OPTIONS` currently rejects `--output`, `--ext-diff`, `--external-diff`, `--exec-path`, `-c`, and `--config-env` for allowed Git commands.
- The classifier already rejects shell chaining, redirection, pipes, command substitution, shell wrappers, network/remote transfer commands, package managers, editors, and common mutating commands.

M8.1 approval remains a mode transition only. After the user clicks `Approve plan and continue`, normal mode policies still apply: allowlisted read-only shell commands may autoexecute, while non-allowlisted shell commands and file writes still follow their existing approval paths.

## Goals

1. Add a narrow set of Git read-only commands to the M6.1 static classifier.
2. Keep the classifier fail-closed: every newly allowed shape must have explicit denied counterexamples.
3. Preserve existing user-visible command cards, audit history, command output capture, cancellation, and local-provider resume behavior.
4. Keep plan mode and non-local-agent paths unchanged.

## Non-Goals

1. Do not add filesystem-mutating commands such as `mkdir`, `touch`, `cp`, `mv`, `rm`, `tee`, or shell redirection.
2. Do not add Git commands that mutate repository state, including `git stash`, `git checkout`, `git switch`, `git branch -d`, `git branch -D`, `git branch -m`, `git branch --move`, `git branch --delete`, `git remote add`, `git remote remove`, `git remote rename`, `git config --set`, `git config --unset`, `git config --add`, or `git config --global --add`.
3. Do not add broad package or language commands such as `cargo`, `npm`, `pnpm`, `yarn`, `python`, or `sed`.
4. Do not add network-fetching commands such as `curl`, `wget`, `npm view`, or broad remote Git operations.
5. Do not autoexecute file-write tools, MCP tools, web tools, subagents, or plan-mode shell commands.
6. Do not trust model-provided `is_read_only`, `is_risky`, or similar fields.

## Behavior

1. When `LocalAgentShellExecution` and `LocalAgentAutoExecuteSafeCommands` are enabled, a local-agent `run_shell_command` request is still classified by `is_local_autoexecute_safe_command`.

2. If a command matches one of the newly allowlisted Git forms below and does not include a denied option or forbidden shell syntax, Warp autoexecutes it through the existing `RequestCommandOutput` / shell command action path.

3. Autoexecuted commands still render the normal command execution UI and return bounded command output to the provider. The user skips only the approval click.

4. If a command is not positively classified as safe, the existing visible approval path remains unchanged. Ambiguous commands require approval.

5. Existing user denylist settings continue to take precedence over static safe-command autoexecute.

6. Plan mode remains read-only and does not autoexecute shell commands. A plan-mode model may propose inspection steps, but shell execution still must not run in plan mode.

7. Approved-plan implementation mode is normal mode. These new allowlist entries may autoexecute there only when the same M6.1 feature flags and user settings permit autoexecution.

8. Shell syntax fail-closed rules remain global. The new Git allowlist must still reject forms with command chaining, pipes, redirection, command substitution, process substitution, backgrounding, or shell wrappers.

9. Model text that claims a command is safe does not affect classification. The command string itself is the only source of static allowlist eligibility.

## New Static Allowlist

Add these Git subcommands to the static allowlist, subject to the global Git deny options and the subcommand-specific restrictions below:

### `git branch`

Allowed read-only forms:

- `git branch`
- `git branch --list`
- `git branch -l`
- `git branch --all`
- `git branch -a`
- `git branch --remotes`
- `git branch -r`
- `git branch --show-current`
- `git branch --contains <rev>`
- `git branch --merged`
- `git branch --no-merged`
- formatting/sorting/verbosity options that do not mutate state, such as `--format=<fmt>`, `--sort=<key>`, `--verbose`, `-v`, and `-vv`

Denied examples that must require approval:

- `git branch -d old`
- `git branch -D old`
- `git branch --delete old`
- `git branch --move old new`
- `git branch -m old new`
- `git branch --copy old new`
- `git branch -c old new`
- `git branch --set-upstream-to origin/main`
- `git branch --unset-upstream`
- `git branch --edit-description`
- `git branch --recurse-submodules`

If implementation cannot robustly distinguish a `git branch` flag as read-only, it must require approval.

### `git remote -v`

Allowed read-only forms:

- `git remote`
- `git remote -v`
- `git remote --verbose`
- `git remote show`
- `git remote show <name>`
- `git remote get-url <name>`
- `git remote get-url --push <name>`
- `git remote get-url --all <name>`

Denied examples that must require approval:

- `git remote add origin <url>`
- `git remote remove origin`
- `git remote rm origin`
- `git remote rename origin upstream`
- `git remote set-url origin <url>`
- `git remote set-head origin -a`
- `git remote set-branches origin main`
- `git remote prune origin`
- `git remote update`

Network-fetching remote maintenance commands require approval even if they appear read-oriented.

### `git config --get`

Allowed read-only forms:

- `git config --get <key>`
- `git config --get-all <key>`
- `git config --get-regexp <pattern>`
- `git config --list`
- `git config -l`
- optional read-only scope selectors with those forms: `--local`, `--global`, `--system`, `--worktree`, `--file <path>`, `--blob <blob>`

Denied examples that must require approval:

- `git config user.name value`
- `git config --set user.name value`
- `git config --add alias.x y`
- `git config --replace-all user.email x`
- `git config --unset user.name`
- `git config --unset-all user.name`
- `git config --remove-section core`
- `git config --rename-section old new`
- `git config --global --add safe.directory /tmp/repo`
- `git config -f .git/config user.name value`

If a `git config` invocation has a key/value assignment shape rather than one of the allowed read operations, it requires approval.

### `git describe`

Allowed read-only forms:

- `git describe`
- `git describe <rev>`
- `git describe --tags`
- `git describe --always`
- `git describe --dirty`
- `git describe --long`
- `git describe --abbrev=<n>`
- `git describe --match <pattern>`
- `git describe --exclude <pattern>`

Denied examples that must require approval:

- any `git describe` command containing global Git config overrides such as `-c`, `--config-env`, `--exec-path`, `--ext-diff`, or output-writing forms
- any `git describe` command using forbidden shell syntax, redirection, or chaining

### `git blame`

Allowed read-only forms:

- `git blame <path>`
- `git blame -- <path>`
- `git blame -L <range> <path>`
- `git blame --line-porcelain <path>`
- `git blame --porcelain <path>`
- `git blame --incremental <path>`
- `git blame --reverse <rev-range> <path>`
- `git blame -w <path>`

Denied examples that must require approval:

- any `git blame` command containing `--contents <file>` or `--contents=<file>` until the implementation explicitly proves that the selected file read stays within existing safety expectations
- any `git blame` command containing global Git config overrides such as `-c`, `--config-env`, `--exec-path`, `--ext-diff`, or output-writing forms
- any `git blame` command using forbidden shell syntax, redirection, or chaining

## Existing Deny Rules That Must Remain

The implementation must keep these existing M6.1 rejects:

- shell wrappers: `sh`, `bash`, `zsh`, `fish`, `pwsh`, `eval`, `exec`, `source`, `.`
- remote/network/file-transfer commands: `ssh`, `scp`, `rsync`, `curl`, `wget`, `nc`, `netcat`, `telnet`
- mutating commands: `rm`, `mv`, `cp`, `touch`, `mkdir`, `rmdir`, `chmod`, `chown`, `sudo`, `tee`
- package/language/editor commands: `cargo`, `npm`, `pnpm`, `yarn`, `python`, `python3`, `pip`, `pip3`, `vim`, `vi`, `nano`, `emacs`, `sed`
- forbidden operators: `;`, newline, `&&`, `||`, `|`, `&`, `>`, `>>`, `<`, `<<`, `<<<`, `2>`, `&>`, `$(`, backticks, `<(`, `>(`

## Acceptance Criteria

1. `git branch` read-only listing forms autoexecute when M6.1 flags/settings permit, while mutating `git branch` forms require approval.
2. `git remote`, `git remote -v`, and read-only URL/show forms autoexecute, while mutating or network-fetching remote forms require approval.
3. Read-only `git config --get` / `--get-all` / `--get-regexp` / `--list` forms autoexecute, while config writes, unsets, section mutation, and key/value assignment forms require approval.
4. `git describe` read-only forms autoexecute, while global override or shell-injection forms require approval.
5. `git blame` read-only forms autoexecute, while `--contents` and shell-injection forms require approval.
6. Existing M6.1 allowlisted commands continue to autoexecute with the feature enabled.
7. Existing M6.1 denied commands and forbidden shell syntax continue to require approval.
8. User denylist settings still override static local safe-command autoexecute.
9. The model cannot force autoexecute by setting or describing a command as read-only.
10. Plan mode still does not autoexecute shell commands.
11. Approved-plan implementation remains normal mode: newly allowlisted commands may autoexecute, but file writes and non-allowlisted shell commands still follow existing approval behavior.
12. No file-write, MCP, web, subagent, package-manager, broad network, or mutating shell command behavior changes.

## Manual E2E Hard Gate

Run on an installed dogfood build with `LocalAgentShellExecution` and `LocalAgentAutoExecuteSafeCommands` enabled.

1. In a Git repository, ask the local agent to inspect branches using `git branch --show-current` and `git branch --all`.
2. Confirm those branch commands run without an approval click and still show normal command cards/output.
3. Ask the agent to inspect remotes using `git remote -v` or `git remote get-url origin`.
4. Confirm the remote read command autoexecutes with a visible command card.
5. Ask the agent to run `git stash`.
6. Confirm `git stash` still requires visible approval and does not autoexecute.
7. Ask the agent to run `git branch -d some-branch`.
8. Confirm the mutating branch command still requires visible approval.
9. Ask the agent to run an injection form such as `git branch && rm -rf /`.
10. Confirm the injection form requires visible approval and nothing autoexecutes.

Source-level tests are not enough for this milestone. At least `git branch` autoexecute and `git stash` denial must be verified in the installed app before PM/user e2e completion.

## Implementation Notes

1. Extend `GIT_ALLOWED_SUBCOMMANDS` only for the approved subcommands.
2. Prefer subcommand-specific classifier helpers over a broad "all git options are safe" rule.
3. Keep global `GIT_DENIED_OPTIONS` in force for every allowed Git subcommand.
4. Add subcommand-specific deny option lists for `branch`, `remote`, `config`, and `blame`.
5. Treat unknown flags for newly allowed subcommands conservatively when mutation risk is unclear. If the implementation cannot prove an option is read-only, require approval and escalate if that blocks the intended user flow.
6. Do not add a path-containment system for shell command arguments in this PR. The safety boundary remains static command classification plus existing shell-command approval fallback.
7. Do not alter `BlocklistAIPermissions` policy semantics except to ensure newly classifier-safe commands flow through the existing local static safe-command path.
8. Do not change command output limits, terminal execution semantics, provider resume/finalize, telemetry shape, or command-card rendering.

## Risk Assessment

- **Git subcommand option drift:** Git has many option aliases, and some read-looking commands can mutate state. Mitigate with explicit allow/deny tests and fail-closed classification.
- **Shell injection:** Existing global forbidden syntax must remain the first gate. Mitigate with regression tests that combine newly allowed commands with chaining, redirection, and command substitution.
- **Network side effects:** `git remote update`, broad package commands, and npm/cargo metadata-style commands can touch network or caches. Keep them out of scope.
- **User working tree mutation:** `mkdir`, `tee`, `git stash`, branch deletion/move/copy, config writes, and file-write tools are out of scope.
- **Over-broad plan approval:** M8.1 plan approval must not become an auto-approve-all execution profile. This spec only changes the static read-only classifier for normal-mode shell commands.

## Escalation Conditions

Escalate before implementation continues if:

1. A proposed Git subcommand or option cannot be confidently classified as read-only.
2. Supporting an allowlisted form requires adding shell redirection, pipes, command chaining, or shell wrapper support.
3. The implementation needs to alter approval policy outside the existing static local safe-command path.
4. Tests reveal existing M6.1 safe-command behavior regresses.
5. Installed-app e2e shows a mutating command autoexecutes or an allowlisted read-only command silently runs without a visible command card.

## PR Split

Single implementation PR is recommended if the diff stays limited to:

- `app/src/ai/agent/local/safe_shell_command.rs`
- existing local autoexecute / run shell command focused tests
- any minimal test fixtures needed for permission fallback coverage

Split only if implementation discovers broader policy or UI changes are required.
