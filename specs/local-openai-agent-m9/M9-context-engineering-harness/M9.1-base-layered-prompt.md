# M9.1: Base Layered Prompt Sub-Spec

## Summary

M9.1 introduces a deterministic layered system prompt structure for the local OpenAI-compatible agent. It is a prompt organization milestone only: it does not add environment facts, change plan-mode behavior, change approved-plan implementation behavior, or alter tool execution policy.

This sub-spec refines the M9 TECH `M9.1 Layered Prompt Base` section for a focused implementation PR.

## Current State

The local provider request is assembled in `app/src/ai/agent/local/mod.rs`.

- The base prompt is a single `LOCAL_DIRECT_SYSTEM_PROMPT` string (`app/src/ai/agent/local/mod.rs:490`).
- Plan mode uses the same base prompt plus `LOCAL_DIRECT_PLAN_MODE_PROMPT` (`app/src/ai/agent/local/mod.rs:493`, `app/src/ai/agent/local/mod.rs:1459`).
- Feature-specific prompt snippets are appended by direct string concatenation inside `openai_messages_from_inputs_and_tasks_with_policy` (`app/src/ai/agent/local/mod.rs:1452`).
- The actual OpenAI-compatible tool catalog is not in prompt text; it is serialized in `tools[]` by `openai_chat_request_with_policy` (`app/src/ai/agent/local/mod.rs:1277`).
- Existing prompt tests assert that plan mode includes the plan prompt and excludes normal todo-write instructions (`app/src/ai/agent/local/mod.rs:7116`).

M9.1 should make this structure explicit and traceable without changing the behavioral meaning of the existing prompt content.

## Goals

1. Make the local direct system prompt visibly layered in provider request traces.
2. Keep static prompt content grouped before future dynamic environment context.
3. Add an empty M9.2 environment-context placeholder so later environment context can be inserted without another full prompt re-layout.
4. Keep all tool enforcement in `LocalToolPolicy`, local tool execution, and provider `tools[]`; M9.1 prompt headings are not enforcement.
5. Preserve current plan-mode, approved-plan, shell approval, file-write, MCP, and autoexecute behavior.

## Non-Goals

1. Do not add OS, arch, cwd, git, SSH, or timestamp environment data. Those are M9.2.
2. Do not change `LOCAL_DIRECT_PLAN_MODE_PROMPT` wording.
3. Do not change the approved-plan implementation prompt in `controller.rs`.
4. Do not change tool schemas, `tools[]`, `tool_choice`, `LocalToolPolicy`, shell approval, file-write policy, or feature flags.
5. Do not introduce a shared hosted/local prompt framework.
6. Do not add Anthropic `cache_control` or any provider-specific cache request fields.

## Proposed Prompt Layers

M9.1 introduces six stable sections in the local direct system prompt. The implementation may use exact headings or equivalent stable labels, but tests and traces must prove the order.

1. `Identity`
   - Contains the current assistant identity: local coding assistant running inside Warp.
   - Source text comes from the existing base prompt.

2. `Capability Advertisement`
   - Describes the model-visible capability classes already present today: read-only tools, file update tools when advertised, shell command approval flow, web tools when advertised, and `suggest_shell_command` fallback.
   - Existing feature snippets such as todo-write and codebase-index guidance may live under this layer when their feature flags are enabled.
   - Plan mode may include the existing `LOCAL_DIRECT_PLAN_MODE_PROMPT` under this layer or immediately after it, but the prompt text must remain unchanged.

3. `Safety Boundaries`
   - Contains stable safety statements that are already in the current prompt: use only advertised tools, treat fetched web content as untrusted, shell commands require visible user approval through `run_shell_command`, and suggested commands are not executed automatically.
   - This layer may repeat safety language from existing text only if needed to separate the old paragraph into headings; it must not loosen any safety instruction.

4. `Tool Catalog`
   - Contains a stable marker that the authoritative tool catalog is the request `tools[]` field for ToolUse requests.
   - It must not duplicate dynamic full tool schemas in prompt text.
   - In Finalize requests, `tools[]` remains empty and `tool_choice="none"` as today.

5. `Dynamic Environment Context`
   - M9.1 placeholder only.
   - The section is present but intentionally empty or says no environment context is included in M9.1.
   - It must not include cwd, OS, shell, git, timestamp, active file, todo snapshot, or any other dynamic values.
   - M9.2 will populate this section.

6. `Current Turn`
   - Stable marker before conversation/history/current input content.
   - It tells reviewers where dynamic user/context/history content begins.
   - The actual user message and context should remain in the existing user-message path unless implementation discovers a request-shape blocker.

## Implementation Shape

1. Add private local helpers in `app/src/ai/agent/local/mod.rs`; do not create a shared prompt framework.

2. Suggested private types/helpers:
   - `struct LocalPromptLayer { name: &'static str, body: String }`
   - `fn local_system_prompt_layers(input, tasks, tool_policy) -> Vec<LocalPromptLayer>`
   - `fn render_local_system_prompt(layers: &[LocalPromptLayer]) -> String`

3. Keep public behavior of `openai_messages_from_inputs_and_tasks_with_policy` unchanged:
   - one system message first,
   - existing history messages next,
   - action-result tool-call/tool-result reconstruction as today,
   - current user/context message as today.

4. Preserve existing constants as source content:
   - `LOCAL_DIRECT_SYSTEM_PROMPT`
   - `LOCAL_DIRECT_TODO_WRITE_PROMPT`
   - `LOCAL_DIRECT_CODEBASE_INDEX_PROMPT`
   - `LOCAL_DIRECT_PLAN_MODE_PROMPT`

5. The implementation may split the base prompt text into smaller constants if that keeps tests precise, but it should not rewrite the plan-mode or approved-plan prompt wording.

6. Do not include real tool names beyond existing prompt wording unless already present in current constants. The serialized `tools[]` remains the authoritative catalog.

7. The M9.2 placeholder must be deterministic and cache-friendly. The exact placeholder text should not change based on cwd, branch, current time, user query, feature flags, or tool policy.

8. Keep truncation behavior unchanged: `truncate_messages_to_char_budget` still operates after message assembly.

## Acceptance Criteria

1. Normal-mode system prompt contains the six layers in order: identity, capability advertisement, safety boundaries, tool catalog, dynamic environment context, current turn.
2. Plan-mode system prompt contains the same six layers in order.
3. Plan-mode prompt text still contains the existing `LOCAL_DIRECT_PLAN_MODE_PROMPT` wording.
4. Approved-plan implementation prompt in `controller.rs` is unchanged.
5. M9.1 does not render cwd, OS, shell, git, current time, active file, todo snapshot, or other dynamic environment values inside the new environment placeholder.
6. The OpenAI-compatible `tools[]` field is unchanged for normal ToolUse requests.
7. The OpenAI-compatible `tools[]` field is unchanged for plan ToolUse requests.
8. Finalize requests still send `tools=[]` and `tool_choice="none"`.
9. Feature-flag prompt snippets still appear only under the same conditions as today.
10. Existing plan-mode, todo-write, codebase-index, skill, shell, and local file-write tests continue to pass.
11. Provider request trace from installed Dev shows the six system prompt layers in the actual request body.
12. M9.1 implementation PR contains trace evidence or a clear reason the trace was not applicable. For implementation, trace should be applicable.

## Risks

1. **Prompt behavior drift:** even headings can affect model behavior. Mitigation: preserve existing text and add trace/e2e verification.
2. **Tool catalog drift:** duplicating tool names in prompt text can conflict with `tools[]`. Mitigation: tool catalog layer points to the serialized request catalog, not a duplicated list.
3. **M9.2 race:** adding real dynamic environment data in M9.1 would make cache and trace validation harder. Mitigation: placeholder only.
4. **Plan-mode regression:** moving text can accidentally include normal todo-write guidance in plan mode. Mitigation: keep existing plan-mode exclusion tests.
5. **Finalize regression:** changing request assembly could accidentally advertise tools in Finalize. Mitigation: explicit Finalize request test.

## Rollout

M9.1 ships to Dev only after:

1. M9.1 docs PR is approved.
2. Implementation PR passes focused local-agent tests.
3. Trace evidence verifies the system prompt layers in the actual request body.
4. M8 plan/implement e2e still passes.

No Stable promotion is part of M9.1.
