# M9: Context Engineering & Harness Architecture TECH

## Context

`PRODUCT.md` defines M9 as a gradual improvement to Warp's local OpenAI-compatible agent: stable prompt layering, bounded environment context, cache-friendly ordering, and a narrower harness that catches model-interaction regressions before user e2e. The important implementation constraint is that M9 should reorganize existing local-agent request assembly, not replace the provider stack or safety policies.

Current local request assembly is concentrated in `app/src/ai/agent/local/mod.rs`:

- `LOCAL_DIRECT_SYSTEM_PROMPT` and related prompt constants are concatenated directly in `openai_messages_from_inputs_and_tasks_with_policy` (`app/src/ai/agent/local/mod.rs:490`, `app/src/ai/agent/local/mod.rs:1468`).
- Plan mode is represented by `LocalToolPolicy::Plan`, which restricts the advertised tool set to read-only/planning tools plus `exit_plan_mode` (`app/src/ai/agent/local/mod.rs:495`, `app/src/ai/agent/local/mod.rs:524`).
- Context is currently rendered from separate `AIAgentContext` variants into text sections (`app/src/ai/agent/local/mod.rs:4708`, `app/src/ai/agent/local/mod.rs:4738`).
- Dynamic facts already include `Directory`, `ExecutionEnvironment`, `CurrentTime`, and `Git`, but they are rendered as general user-context text rather than one stable labeled environment block (`app/src/ai/agent/local/mod.rs:4740`, `app/src/ai/agent/local/mod.rs:4754`, `app/src/ai/agent/local/mod.rs:4770`, `app/src/ai/agent/local/mod.rs:4787`).
- Provider request shape is generated by `openai_chat_request_with_policy`, where ToolUse requests advertise tools and Finalize requests intentionally pass no tools with `tool_choice="none"` (`app/src/ai/agent/local/mod.rs:1277`, `app/src/ai/agent/local/mod.rs:1292`).
- Usage telemetry already understands cache read/write token fields when providers return them (`app/src/ai/agent/local/mod.rs:5488`).
- Action-result resume is deliberately narrow: user queries and shell/MCP action results re-enter ToolUse; other no-query resumes finish early (`app/src/ai/agent/local/mod.rs:703`, `app/src/ai/agent/local/mod.rs:1392`, `app/src/ai/agent/local/mod.rs:1423`).

The controller owns the request inputs and should remain the boundary for collecting session context. `input_context_for_request` already appends current time and active-session execution environment after pending user context (`app/src/ai/blocklist/controller/input_context.rs:51`). `resume_conversation` and normal query paths reuse that function, so M9 should add bounded environment data there or immediately adjacent to it rather than creating a second source of truth (`app/src/ai/blocklist/controller.rs:1600`, `app/src/ai/blocklist/controller.rs:2771`).

External baseline findings:

- Claude Code has explicit permission/default modes, plan-related settings, and auto/bypass modes, but public docs do not present branch/undo as core universal state-machine states.
- Codex CLI has sandbox/approval modes, interactive follow-up input, shell-result injection, and a transcript fork affordance. The fork affordance is product-specific and should not become M9 V0 unless Warp designs matching UX.
- Cursor and Aider both expose plan/ask versus build/edit workflows; Aider documents `ask`, `code`, and `architect` modes as the normal planning/implementation split.
- Common denominator for M9.4 V0 is therefore: plan, approved implementation, normal follow-up, and action-result resume. Branch/fork and undo/retry are V1+.

## Open Question Decisions

| OQ | Decision | Reason |
| --- | --- | --- |
| 1. Environment context layer | Render as an independent labeled section at the end of the system message for M9.2, after stable base/mode/safety prompt text and before user history is interpreted. | Keeps the static prefix stable while making context visible in request traces. Avoids creating a synthetic user message that could be mistaken for user intent. |
| 2. SSH environment context | Include `session_type=ssh`, remote cwd, shell, OS/arch when known, and `local_writes_disabled=true` when local file tools cannot safely write the remote filesystem. | The model needs enough context to plan correctly, but tool policy still enforces safety. |
| 3. Harness state V0 | V0 covers `Plan`, `PendingPlanApproval`, `ApprovedImplementation`, `FollowUp`, and `ActionResultResume`. It does not implement branch/fork or undo as first-class states. | This matches the common official-agent baseline and the user's request to keep M9.4 small. |
| 4. Cache metadata missing | Treat cache metadata as optional. If available, map it into existing usage telemetry; if absent, log/trace absence and preserve behavior. | Prompt ordering must improve correctness/inspectability independent of provider cache support. |
| 5. Environment context size | V0 hard cap: 500 tokens equivalent, implemented as a conservative character cap plus field-level truncation. | Prevents environment bloat and reduces prompt-cache churn. TECH implementation can tune exact constants. |

## Proposed Changes

### M9.1 Layered Prompt Base

**Status: Merged — PR #68 (2026-06-27)**

Introduce a small local request-layer abstraction inside `app/src/ai/agent/local/mod.rs`, not a new prompt framework. The target shape is:

1. Stable base instructions.
2. Stable mode/tool instructions.
3. Stable safety constraints.
4. Dynamic labeled environment context.
5. Dynamic project/file/rule/context sections.
6. Conversation history and current input.

Implementation plan:

- Add `LocalPromptLayer` or equivalent internal helper that returns named text sections. Keep it private to `local/mod.rs` for V0.
- Split current concatenation in `openai_messages_from_inputs_and_tasks_with_policy` into helper functions such as:
  - `stable_base_prompt(tool_policy)`
  - `stable_feature_prompt_layers(input, tool_policy)`
  - `dynamic_context_layers(input)`
- Keep plan-mode tool filtering in `LocalToolPolicy`; do not use prompt text as enforcement.
- Keep existing message roles: one system message, existing history/tool messages, one user message when needed. M9.1 should primarily make system message composition deterministic and testable.
- Add snapshot-style tests that compare layer order and prove dynamic values do not appear before the dynamic boundary.

API/files:

- `app/src/ai/agent/local/mod.rs`: prompt layer helpers, tests.
- No proto/schema/API changes.
- No UI changes.

Trace/e2e:

- PR description must include a request-body trace showing the system message layer order in normal mode and plan mode, or a local mocked provider capture that records the serialized OpenAI request body.

### M9.2 Environment Context Block

**Status: Merged — PR #70 (2026-06-28)**

Add a bounded `AIAgentContext::Environment` variant or a private local-agent environment render helper. Prefer a new context variant if the same data should survive through history/task conversion; prefer a private helper if the data can be derived at request-build time without persistence. The implementation should decide after checking proto/persistence impact, but the rendered provider text must be one labeled block.

V0 fields:

- `session_type`: `local`, `ssh`, or `unknown`.
- `os`: family/category plus distribution/version when known.
- `arch`: CPU architecture when known.
- `shell`: shell name plus version when known.
- `cwd`: current working directory.
- `writable_root`: same as cwd-derived writable root when local file tools use that boundary.
- `git_branch`: current branch when known.
- `git_head`: head commit short/full value already available from `AIAgentContext::Git`.
- `git_modified_files_count`: count only, not full file list.
- `process_name`: terminal process name when available from active session.
- `current_time`: dynamic timestamp, placed in dynamic context, not stable prefix.
- `local_writes_disabled`: true for SSH/remote cases where local sync file tools are unavailable.

Explicitly excluded:

- Environment variable values.
- API keys, provider credentials, tokens, cookies, `.env` contents.
- Full file contents.
- Full git history, full `git status`, or unbounded file lists.
- Full process list or shell startup files.

Implementation plan:

- Extend `input_context_for_request` or adjacent helpers to collect missing bounded facts from `ActiveSession`.
- Reuse existing `AIAgentContext::Directory`, `ExecutionEnvironment`, `CurrentTime`, and `Git` where possible; avoid duplicating facts in both old sections and the new block. After the environment block ships, individual legacy sections should either be folded into it or omitted when already represented.
- Add `environment_context_section(input)` with deterministic field order and per-field truncation.
- Enforce the V0 size cap in the renderer, not only at collection time.
- Use explicit `unknown` only when absence is meaningful; otherwise omit unavailable optional fields.

API/files:

- `app/src/ai/agent/mod.rs` or context type owner if adding `AIAgentContext::Environment`.
- `app/src/ai/blocklist/controller/input_context.rs`: collect bounded environment fields.
- `app/src/ai/agent/local/mod.rs`: render one labeled environment block.
- Tests in `app/src/ai/agent/local/mod.rs` and controller context tests if a new context variant is added.

Trace/e2e:

- Request trace must show `Environment context:` in normal mode, plan mode, and approved-plan implementation.
- Dev e2e: `/plan` flow in a known cwd shows correct cwd/writable root and still completes write_file + cargo test.

### M9.3 Cache-Friendly Ordering and Telemetry

**Status: Merged — PR #71 (2026-07-02)**

M9.3 should not add correctness dependence on prompt caching. It only makes the OpenAI-compatible request more cache-friendly and records provider metadata when available.

Implementation plan:

- Keep stable prompt layers byte-for-byte stable when only cwd, branch, timestamp, selected file, todo snapshot, or user query changes.
- Keep all dynamic context after the stable prompt boundary.
- For OpenAI-compatible Chat Completions, treat cache "placement" as stable-prefix ordering. Do not add a `cache_control` field to OpenAI-compatible requests unless the configured provider explicitly supports it.
- For Anthropic, explicit `cache_control` breakpoints are provider-specific and V1+ unless Warp adds a separate Anthropic request path. The M9 V0 OpenAI-compatible path should document where the breakpoint would live conceptually, but not serialize Anthropic fields.
- Preserve current OpenAI-compatible `stream_options.include_usage` fallback: if the provider rejects usage options, retry without usage and mark usage unavailable.
- Extend tests around `OpenAIStreamUsage` and `stream_finished_done` only if new metadata fields are introduced. Current cache read/write mapping already covers `cached_tokens` and `cache_creation_tokens`.
- Add trace evidence that two requests differing only in cwd/time have the same stable prefix through the dynamic boundary.

API/files:

- `app/src/ai/agent/local/mod.rs`: ordering tests and optional usage parsing extensions.
- `app/src/ai/agent/local/pricing.rs`: only if new cache metadata changes cost calculations.
- No UI changes unless usage display needs a separate follow-up.

Trace/e2e:

- PR description must include request-prefix diff evidence and provider usage evidence when available. If new-api omits cache fields, explicitly show graceful absence.

### M9.4 Harness State Machine, Narrowed V0

**Status: Merged — PR #72 (2026-07-02)**

Do not create a large product state machine. Add a local-agent harness helper that can script request input, mocked provider responses, local tool results, and expected serialized request properties.

V0 states:

- `Plan`: user submitted plan-mode query; request uses plan tool policy and cannot execute mutating tools.
- `PendingPlanApproval`: model called `exit_plan_mode`; controller displays approval state.
- `ApprovedImplementation`: user approved; request includes approved plan and normal tools.
- `FollowUp`: normal user query or resume after completed turn; request includes relevant history and current environment.
- `ActionResultResume`: shell/MCP result resumes ToolUse when more tools are needed.

Out of scope for V0:

- Branch/fork conversation UX.
- Undo/retry UX.
- Cursor-style checkpoints.
- Background-agent worktree management.
- Any new native UI state beyond what M8 already has.

Implementation plan:

- Add test helpers around existing `openai_messages_from_inputs_and_tasks_with_policy`, `openai_chat_request_with_policy`, and local provider stream fixtures.
- Prefer small focused tests over a framework that mirrors production state. The harness should assert serialized request shape, tool catalog shape, and stream state transitions.
- Reuse existing tests for `local_direct_tool_round_limit`, plan-mode injection, action-result conversion, file-write cards, and code-diff behavior; add only the missing multi-turn glue.

API/files:

- `app/src/ai/agent/local/mod.rs`: request-shape harness helpers and tests.
- `app/src/ai/blocklist/controller.rs` tests only if approval-state transitions need controller-level coverage.
- No new user-facing state enum unless an implementation PR proves existing state cannot express a required transition.

Trace/e2e:

- Request trace for approve path: plan ToolUse with plan tools, approve implementation ToolUse with normal tools, shell/MCP action-result resume ToolUse with tools present.

## Parallelization

Do not parallelize M9.1-M9.3 implementation. Prompt layering, environment context rendering, and cache-friendly ordering touch the same request assembly code and must land sequentially to keep trace evidence interpretable.

M9.4 can start after M9.1 request-layer helpers exist. M9.5 must be last. If parallel agents are used later, use one local worktree per PR:

- `../warp-m9.2-env` on `yi/m9.2-local-agent-environment-context`
- `../warp-m9.4-harness` on `yi/m9.4-local-agent-core-state-harness`

Do not run them against the same checkout. Merge order remains M9.1 → M9.2 → M9.3 → M9.4 → M9.5.

## Risks and Mitigations

- **Sensitive data leakage:** use allowlisted fields only; test explicit deny cases.
- **Prompt regression:** keep one system message and existing tool-policy enforcement; verify with request traces before user e2e.
- **Cache overfitting:** treat cache metadata as telemetry, not correctness.
- **Harness overreach:** keep V0 to common official-agent states; branch/fork and undo are deferred.
- **Provider incompatibility:** maintain current retry-without-usage behavior and avoid Anthropic-specific fields in OpenAI-compatible requests unless gated.

## Follow-Ups

- V1+: explicit Anthropic cache breakpoints if Warp adds a provider-specific Anthropic request path.
- V1+: Cursor/Codex-style fork/checkpoint UX only after product design.
- V1+: long-term project memory and user-editable prompt layers.
