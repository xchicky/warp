# M7.1: SSH-Aware Local Agent Tools

## Summary

Make local OpenAI-compatible agent tools SSH-aware for V0. In a Warpified SSH session, `run_shell_command` should reach the existing `RunShellCommand` / `RequestCommandOutput` / `ShellCommandExecutor` path instead of failing local cwd validation, while local filesystem tools should fail early with a clear SSH-specific error that points the model toward shell inspection commands.

## User Story

As a Warp user connected to an SSH session, I want the local agent to inspect the remote shell with `run_shell_command`, and I want unsupported file tools to explain the limitation instead of reporting local filesystem errors.

## Scope

V0 covers Warpified SSH sessions only. Docker exec, WSL, containers, subshells, and other future remote terminal types are out of scope and should keep current behavior unless they are represented by the same explicit `SessionType::WarpifiedRemote` signal.

No feature flag is required. This is a correctness fix for already-dogfooded local shell execution and local filesystem tools.

## Proposed Changes

### 1. Session-Type Context Plumbing

Recommended approach: add a local-only runtime/tool context, not a prompt-facing `AIAgentContext` variant.

Add a small context type near the local-direct execution path, for example:

```rust
#[derive(Clone, Copy, Debug, Default, PartialEq, Eq)]
pub struct LocalToolRuntimeContext {
    pub session_is_local: Option<bool>,
}

impl LocalToolRuntimeContext {
    fn is_ssh_session(self) -> bool {
        self.session_is_local == Some(false)
    }
}
```

The exact name is implementation-owned, but the semantics should be:

1. `Some(true)` means the active session is local.
2. `Some(false)` means the active session is explicitly remote/SSH for M7.1 purposes.
3. `None` means unknown; fail closed to existing behavior.

Plumb this from the request layer into the local provider:

1. In `RequestParams::from_request_input`, derive the value from `session_context.session_type()` while the request still has session access.
2. Store it in `RequestParams` or in `LocalDirectConfig`; prefer a separate request/runtime field over `LocalDirectConfig` if practical, because base URL/model config and terminal execution context are separate concepts.
3. Pass it through `local_direct_config_for_request` / `generate_openai_compatible_output`.
4. Pass it into `execute_local_tool_batch_with_policy`, then into `execute_local_tool_with_policy` and `execute_run_shell_command_tool`.

Do not infer SSH from cwd strings, `Path::exists`, or `canonicalize` failures. `/tmp`, `/home/user`, a deleted local cwd, and a Docker cwd can all create misleading filesystem signals.

Do not expose this context to the model by adding it to the rendered prompt unless a later spec needs that UX. M7.1 uses session type to decide tool execution policy, not to teach the model about remotes.

If implementation finds that a prompt-facing `AIAgentContext` variant is significantly cheaper than request/runtime plumbing, pause and ask PM before switching approaches.

### 2. `run_shell_command` SSH Fix

Make `resolve_run_shell_command_cwd` SSH-aware by adding an explicit session/runtime argument.

For local sessions:

1. Keep the existing active cwd `canonicalize` and `is_dir` checks.
2. Keep the existing cwd override behavior, including the "override must match active terminal cwd" rule.
3. Preserve existing validation for empty commands, NUL bytes, `rationale`, `timeout_ms`, and feature flags.

For SSH sessions:

1. Require a non-empty active cwd string/path from context, but do not canonicalize it against the local filesystem.
2. Do not call `Path::exists`, `fs::metadata`, or `is_dir` for the active cwd.
3. Reject any `cwd` argument explicitly with an SSH-specific message, such as `cwd overrides are not supported in SSH sessions; run_shell_command uses the active remote terminal cwd`.
4. Return the active cwd for display in the pending tool response.
5. Let the existing `RunShellCommand` card / `RequestCommandOutput` / `ShellCommandExecutor` path own approval, execution, output capture, result resume, M6.1 autoexecute, and UI audit behavior.

For unknown session type:

1. Keep current local behavior for compatibility.
2. Do not silently treat unknown as SSH.

No changes are expected in `RequestCommandOutputResult` resume serialization for this milestone; PR #39 already fixed shell/MCP history pairing, and PR #4 already maps `RequestCommandOutputResult` back into OpenAI tool messages.

### 3. Other Filesystem Tools SSH Short-Circuit

Add one dispatch-level guard in or immediately before `execute_local_tool_with_policy`.

When `LocalToolRuntimeContext::is_ssh_session()` is true and the tool name is one of:

- `read_file`
- `grep`
- `glob` / FileGlobV2
- `list_directory`
- `search_codebase`
- `apply_file_diff`
- `write_file`
- `edit_file`

return a tool error with this exact user/model-facing text:

```text
tool not supported in SSH session, use run_shell_command to inspect remote files via cat/grep/ls
```

This guard should run after the existing `tool_policy.denied_tool_error` check so plan mode, subagent policy, or deny policy still gets the more specific policy error where applicable. It should run before feature-flag gates and before per-tool filesystem work, so SSH users do not see local-only flag or cwd/canonicalize errors for these fs tools.

Do not add SSH catch-all filesystem fallback handling inside `apply_file_diff.rs`, `codebase_index.rs`, or individual tool implementations unless tests prove the centralized dispatch cannot cover a tool path.

Web tools, MCP tools, `todo_write`, `exit_plan_mode`, `spawn_subagent`, `suggest_shell_command`, and `run_shell_command` are not part of the fs short-circuit list.

## Acceptance Criteria

1. Local-direct request construction derives explicit session locality from `SessionType`, not from cwd string or local filesystem probes.
2. The derived session locality reaches the local tool execution layer for both first-turn tool calls and continuation/finalize tool rounds.
3. Unit tests cover local, SSH/remote, and unknown session context behavior at the plumbing boundary.
4. In an SSH session, `run_shell_command` no longer returns `Current working directory is not readable` for a remote cwd such as `/home/zhangyi`.
5. In an SSH session, `run_shell_command` skips local `canonicalize`, `exists`, `metadata`, and `is_dir` checks for the active cwd.
6. In an SSH session, `run_shell_command` rejects any explicit `cwd` override with a clear SSH-specific error.
7. In a local session, `run_shell_command` keeps existing cwd validation, cwd override restrictions, command validation, pending-card behavior, and existing test expectations.
8. `run_shell_command` still emits the existing pending `RunShellCommand` tool card and resumes from `RequestCommandOutputResult`; no direct local process execution is introduced.
9. In an SSH session, each fs tool in the short-circuit list returns the exact friendly error text specified above.
10. The friendly fs error is produced at dispatch level before per-tool local filesystem code runs.
11. The fs short-circuit list is covered by a table test that asserts all listed tool names share the same error text.
12. Non-fs tools, MCP tools, `todo_write`, `suggest_shell_command`, and `run_shell_command` are not accidentally blocked by the fs short-circuit.
13. Docker exec / WSL / subshell / unknown remotes are not newly classified as SSH unless represented by `SessionType::WarpifiedRemote`; V0 does not attempt cwd-based remote detection.
14. No new product telemetry, billing fields, or model-visible context is added for SSH detection.
15. Existing local-agent tests, including shell execution, autoexecute safe commands, MCP result pairing, file tools, and plan/subagent policy tests, continue to pass.

## Risks And Mitigations

- Local regression: plumbing session context into the local-direct path touches request construction and tool execution. Mitigate with local-session tests and the full existing local-agent suite.
- False positive SSH detection: treating a local session as SSH would skip local cwd validation for shell commands and block fs tools. Mitigate by deriving only from `SessionType::WarpifiedRemote`, not cwd.
- False negative SSH detection: an SSH session that arrives as unknown would keep current `cwd not readable` behavior. Mitigate with explicit tests around `SessionType::WarpifiedRemote` and e2e on a real SSH session.
- Error inconsistency: one fs tool using a different error damages model recovery. Mitigate with a single constant and table tests over the full fs tool list.
- Over-scoping into remote filesystem support: V0 intentionally avoids SSH file APIs and edit support. Mitigate by short-circuiting unsupported fs tools and directing inspection through `run_shell_command`.

## PR Split

Preferred split:

1. PR1: session-type runtime plumbing plus SSH-aware `run_shell_command`.
2. PR2: fs tool SSH short-circuit.

PR1 gives the user the highest-value SSH shell path quickly. PR2 is an experience polish and trust fix for unsupported tools. A single PR is acceptable if implementation stays compact and the tests remain easy to review.

- No Docker/container remote detection.

## Parallelization

Use one implementation owner per PR. The changes are small but cross the request construction and local tool execution boundary; splitting work across parallel agents would create coordination overhead and likely duplicate tests. Agent2 should review PR1 before PR2 starts so the runtime context shape is settled before fs short-circuit work depends on it.
